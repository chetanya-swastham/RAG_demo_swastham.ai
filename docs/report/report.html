1Executive summary

Swastham users ask health questions in English, Hindi and Hinglish. When an AI model answers each language separately, the answers drift apart: facts, numbers and even safety warnings differ between languages. For a health product, that is a patient-safety risk.

I designed and built a retrieval-augmented generation (RAG) system that removes this risk by design. Every question, in any language, is answered once in English from the verified knowledge base. Hindi and Hinglish users receive a checked translation of that exact answer. The translation is automatically back-translated and must keep every number, safety caution and recommendation. If it doesn't, the answer is blocked rather than shown or spoken.

What was delivered

  • The brief, fully met: an English knowledge base indexed in FAISS, a structured Answer Plan, one canonical English answer, lightweight validation, and a UI to compare English and Hindi side by side.
  • Beyond the brief, each built on the same "one answer" rule:
    • fail-closed translation safety gates;
    • question canonicalisation with an answer store (same question, same answer, every time);
    • full Hinglish support;
    • a trilingual evaluation suite;
    • a voice assistant and a hands-free voice agent that understands follow-up questions.
  • Deployed to the cloud as a container on Vercel, and documented for handover (README, implementation guide, 81 offline tests).

How problems were solved

Early testing showed Hindi answers quietly losing a doctor referral and softening an insulin warning. I built a runtime trace that logs every retrieval and model call, found the root cause (the translation step, not the architecture), and fixed it in the prompts, the medical glossary and new safety gates. I never lowered a quality threshold to make a test pass. Section 6 walks through these investigations.

2The problem

A common way to support Hindi is to let the AI model answer a Hindi question directly in Hindi. That produces two independent answers to the same question, one per language. They are generated separately, so they can say different things:

  • Different facts or detail: the Hindi answer is often shorter and less specific.
  • Lost numbers: a BMI cut-off or a walking target can change or disappear.
  • Lost safety cautions: for example, "people on insulin must adjust their dose with their doctor" can go missing. This is the most serious risk.
Why it matters for Swastham: a Hindi-speaking user with type 2 diabetes who is on insulin must get exactly the same safety warning as an English-speaking user. An answer that is "mostly the same" is not acceptable in healthcare.

The original brief

Take an English knowledge document on obesity, diabetes and the Dixit Lifestyle, and make sure the same question in English and Hindi rests on the same evidence and the same underlying answer. Hindi must never reason on its own. The brief also asked to keep the stack simple: Python, PyMuPDF, sentence-transformers, FAISS and one LLM, with no separate Hindi vector database, no agent frameworks, no hybrid search and no reranking.

3The solution: generate once, translate everywhere

The core design decision is simple and strict: Hindi and Hinglish never reason on their own. Every language goes through the same English answer path. Other languages only get a translation, and that translation must pass checks before anyone sees or hears it.

Design principles I applied

PrincipleWhat it means in the system
Generate once, translate everywhereOnly one function writes medical content. Hindi, Hinglish and speech are all derived from that one English answer
Same meaning → same answerQuestions are canonicalised and answers are stored per canonical question, so repeat questions get identical answers in seconds
Validate translations like any model outputScript, number and medical-term gates run on every translation, then a back-translation parity check
Fail closed on safetyA translation that loses a number or a safety caution after one retry is never shown or spoken
Fix causes, not thresholdsEvery failure was fixed in the prompt, glossary or pipeline. No threshold was ever lowered
Deterministic and testableTemperature 0 with a fixed seed. All checks are pure functions, unit-tested offline without an API key

5Features I added

Each feature started from a concrete need. Each one keeps the core rule: one canonical English answer per question, with every other language a checked translation of it.

SafetyParity checks and fail-closed translation gates

WhyA translation can silently drop a warning. The first traces proved it happens.
HowEvery translation passes these checks:
  • Gates: correct script, identical numbers, medical terms present.
  • Back-translation to English, then five parity checks: evidence overlap, numbers, safety cautions, recommendations and content coverage.
  • On failure, one retry with the failed checks as feedback.
OutcomeIf the numbers or safety cautions are still wrong after the retry, the answer is blocked. A user never sees or hears an unverified translation.

ConsistencyQuestion canonicalisation and answer store

Why"Can I eat fruit?" and "Are fruits OK for me?" are the same question and must get the same answer.
HowEach question is rewritten into one standard English question, cached per wording. Validated answers and passing translations are stored per canonical question. A fingerprint of the model, prompts, glossaries and knowledge base resets the store automatically when any of them change.
OutcomeRepeat questions are answered identically in a few seconds, instead of the 50–80 seconds a new question takes on the free API tier.

LanguageHinglish (Romanised Hindi) input and output

WhyMany users type Hindi in English letters, mixed with English words. Embedding that text directly retrieves the wrong evidence (overlap 0.21 with English).
HowHinglish questions go through a pipeline and join the existing Hindi path. Answers come back through the same checks as Hindi.
  • Detection: scored strong and weak marker words, with no model call.
  • Normalisation: one standard spelling per Hindi word (mai → main, hu → hoon).
  • Protection: medical terms such as HbA1c, glimepiride and insulin are masked before conversion.
  • Conversion: a checked step from Roman script to Devanagari.
OutcomeEvidence overlap with English rose from 0.21 to 1.00, on 14 of 14 questions. All four forms below reach the same canonical question and the same evidence:
EN  Can I eat fruits if I have diabetes?
HI  अगर मुझे डायबिटीज है तो क्या मैं फल खा सकता हूँ?
HG  Mujhe diabetes hai, kya main fruits kha sakta hu?
HG  kya mai fruit kha sakta hu diabetes me

QualityTrilingual evaluation suite

Why"It looks right" is not evidence. Consistency across languages had to be measured.
HowA dataset of 14 EN/HI/Hinglish triples (5 safety-critical) with spelling variants. The suite measures:
  • retrieval consistency, evidence overlap and missing evidence;
  • plan consistency and answer similarity;
  • hallucination rate and parity.
Each language runs separately, so convergence is measured rather than forced. The Hinglish normaliser is compared against two baselines. Reports are produced as Markdown, JSON and CSV.

VoiceVoice assistant and hands-free voice agent

WhyMany users prefer speaking to typing, especially in Hindi.
HowVoice only adds input and output around the same verified pipeline, so what is spoken is the checked answer.
  • Speech in: Whisper, with Urdu-script output corrected to Hindi and silence rejected.
  • Speech out: neural Hindi and Indian-English voices.
  • Voice agent: microphone calibration to room noise, pause detection and 3-turn memory. It rewrites follow-ups such as "और अगर मैं प्रेग्नेंट हूँ तो?" into standalone questions, lets you interrupt it (barge-in), and shows a ✓ verified badge.
OutcomeThe live Hindi round trip was transcribed exactly. A two-turn pregnancy follow-up was rewritten correctly, answered in Hinglish, and passed validation and parity. If it cannot verify an answer, the agent says so and refers the user to their doctor.

ProductParity Compare UI, web app and cloud deployment

WhatA three-tab web app with no build step.
  • The Ask tab shows a full pipeline trace and the evidence behind each answer.
  • The Parity Compare tab scores English, Hindi and Hinglish side by side against the old "answer directly in Hindi" baseline. It refuses to compare different questions (Question Intent Mismatch).
The app is containerised with CPU-only PyTorch and the embedding model preloaded, and deployed on Vercel with the API key kept in the platform's environment variables.

6Problem solving: case studies

I found these problems with a runtime trace tool (trace_parity.py) that logs every retrieval and every model call for the sample questions. The trace showed that the architecture was right, with one retrieval, one generation, and the exact answer passed to the translator. The translation itself was unfaithful. So every fix went into the translation step.

Case 1A check that passed and hid a bug (BMI)

SymptomThe BMI sample "passed" parity.
Root causeThe translator had returned the English text unchanged, so English was being compared with English.
FixA gate that rejects a "Hindi" answer that is not mostly Devanagari, plus a rule that the output must always be Hindi, with the instruction repeated after the source text.
LessonEvery check needs a sanity check on its inputs. A passing check can hide a bug.

Case 2Doctor referral lost in translation (pregnancy)

SymptomThe safety check failed on the Hindi pregnancy answer.
Root cause"Obstetrician" was translated as प्रसूति विशेषज्ञ ("obstetric specialist"), which did not back-translate as a doctor referral.
FixReferral roles (clinician, obstetrician, paediatrician, endocrinologist, healthcare team) were added to both glossaries, with a rule to keep the specific professional named.

Case 3An insulin warning made weaker (insulin)

SymptomThe recommendation check failed.
Root cause"Clinician" collapsed to "doctor", and "will almost certainly need to be adjusted" became "adjusted fairly precisely". The certainty of a safety instruction was weakened.
FixPrompt rules to keep certainty words and the named professional, and the answer sent inside explicit delimiters. Exact-number gates with one retranslation, then fail closed.

Case 4Tense drift and a glossary over-reach (hunger)

SymptomThe recommendation check failed on the hunger sample.
Root causeThree faults:
  • "Take medicines" became "are taking", losing the instruction.
  • "Diabetes" was expanded to "type 2 diabetes" from the glossary.
  • A heading was left in English.
FixSeparate glossary entries for related terms, a rule to use a glossary term only where the English uses that exact term, and rules to keep tense and translate headings.
ResultInsulin, BMI, pregnancy and hunger all pass 7 of 7 checks, with no threshold or scoring logic changed.
Other issues solved along the way:
  • Whisper labels spoken Hindi as Urdu, so the app re-transcribes it as Hindi.
  • Whisper invents "Thank you." on silence, so silent segments are filtered out.
  • The model's reasoning tokens were cutting answers short, so the output budget was raised and cut-offs now raise an error instead of showing a partial answer.
  • Keyword checks matched the middle of words (kid in kidney), so they now match whole words only.
  • Stale stored answers are now discarded automatically by the fingerprint.

Engineering practices

  • Determinism: temperature 0 and seed 42 on every model call, with stored answers for repeatable output.
  • No silent fallback: truncated or empty model output raises an error, so the demo never shows a partial or invented answer.
  • Resilience: automatic retries on rate limits, server errors and timeouts (up to 8 attempts).
  • Safe storage: the answer store is written atomically under a lock, and only validated answers are stored.
  • Separation of concerns: ingestion, LLM layer, pipeline, validator, Hinglish, voice, server and UI are separate modules. Adding a new language touches only the translation layer (see the implementation guide, §17).

8Limitations and recommended next steps

This is a proof of concept. These are its known limits, stated plainly, with the step I recommend for each before production.

Limitation todayRecommended next step
The checks are keyword-based, so they raise some false alarms. For example, "talk with your doctor" can be missed where the check looks for "consult a healthcare professional"Add meaning-level checks (an entailment model or an LLM judge) alongside the keyword checks
A new question takes 50–80 s on the free API tier (6–10 model calls). Repeat questions take secondsA paid tier or a faster model; pre-warm the store with the most common questions
Slightly different canonical wordings ("BMI cut-offs" vs "cut-off") are stored separatelyReuse a stored answer when the evidence is identical and the questions are very similar (cosine ≥ ~0.9)
The medical glossary determines whether advice survives translationVersion the glossary and have a clinician review it. Rerun all samples after each change
The system answers only from the knowledge documentExtend the knowledge base. Re-ingesting resets stored answers automatically
Voice pause detection is energy-based, and Hinglish speech is transcribed in DevanagariUse a speech-activity model. "Reply in: Hinglish" already handles the reply language

Roadmap to production

  1. Clinical review of the glossary and the safety-caution rules.
  2. Meaning-level validation alongside the keyword checks.
  3. More languages (e.g. Marathi, Tamil). The architecture needs only a new checked translator and a voice for each; retrieval, planning and validation stay unchanged.
  4. Integration with the Swastham app: authentication, logging and monitoring of parity failures, and a larger evaluation set drawn from real user questions.

AAppendix: how to run and demo

Use the live app

Open https://swastham-rag-demo.vercel.app in Chrome or Edge. Voice needs microphone permission.

Source code

GitHub repository: {{REPO_URL}}

Run it locally

You need Python 3.10+, internet access and a free Groq API key from console.groq.com/keys.

git clone {{REPO_URL}}.git
cd RAG_demo_swastham.ai
pip install -r requirements.txt
copy .env.example .env          # then set GROQ_API_KEY in .env
python server.py                # open http://localhost:8000

The search index and stored answers are included in the repository, so you don't need to re-ingest. To rebuild the index, run python ingest.py --source documentRAG.md. The first run downloads the embedding model (about 90 MB).

Run the tests and evaluations

python -m unittest test_parity.py test_hinglish.py test_voice.py   # 81 offline tests, no key needed
python evaluate.py                                                 # 15 EN/HI pairs vs baseline
python -m evaluation.run_trilingual_eval --retrieval-only          # EN/HI/Hinglish consistency report

Suggested 5-minute demo

  1. Ask tab: ask the Hindi insulin question and open the Pipeline trace. It shows the canonical question, the evidence, the Answer Plan, the validation and the parity checks.
  2. Parity Compare: run the Insulin (safety) sample with Show baseline ticked. The canonical pipeline passes, and the old approach is scored alongside it.
  3. Voice Agent: set Reply in: Hinglish, then say "I take insulin for type 2 diabetes, can I follow the Dixit two-meal plan?" and follow up with "aur agar main pregnant hoon to?". Interrupt it mid-answer to see barge-in.
